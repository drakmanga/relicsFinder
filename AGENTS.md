# Relic Finder - Frontend Engineering Rules

> This is the repository's `AGENTS.md`. It is written for the coding agent, not
> for a human reader.
> Every rule below is imperative and mechanically checkable.
> When a rule and a convenience conflict, the rule wins.

---

## 0. How to use this file

Before writing or editing any frontend code in `apps/web/` or `packages/ui/`, read this file in full.
Do not skip a rule because the change "looks small": most of the debt catalogued in section 9 arrived one small change at a time.

When you finish a task, run the verification block in section 8 and report the actual output.
Never claim a task is done on the basis of "the code looks right".

---

## 1. The ten non-negotiables

| #   | Rule                                                            | Fails when                                                                       |
| --- | --------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| 1   | No inline `style={{ ... }}` in JSX carrying visual values       | any `style={{}}` containing a colour, spacing, size, radius, duration or z-index |
| 2   | No magic values                                                 | any raw hex, `px`, `ms` or unitless spacing number outside `tokens.css`          |
| 3   | Every font-size is `rem`, never `px`                            | `font-size: 15px` anywhere, including the root                                   |
| 4   | Components stay under ~150 LOC                                  | a `.tsx` file over 150 lines without a written justification at the top          |
| 5   | Every interactive element is reachable and operable by keyboard | a click handler on a non-button, a missing `:focus-visible` style                |
| 6   | Every layout survives 360px width and 200% text zoom            | horizontal scrollbar on the document, clipped or overlapping text                |
| 7   | Touch targets are at least 44x44 CSS px                         | any button, icon button or row action below that box                             |
| 8   | `tokens.json` is the only source of design values               | a value edited in `tokens.css` without regenerating it                           |
| 9   | Reusable UI lives in `packages/ui`, app UI in `apps/web`        | a generic component (button, badge, layout primitive) defined inside `apps/web`  |
| 10  | Every non-obvious decision carries its reason in a comment      | a workaround, a magic constant or an override with no `why`                      |

## 2. Where things live

```
design-system/
  tokens.json          SOURCE OF TRUTH for every design value
  DESIGN_SYSTEM.md     the written spec; update it when a rule changes
packages/ui/
  src/styles/
    tokens.css         GENERATED from tokens.json - never hand-edit
    base.css           element defaults + typography scale
    geometry.css       clip-path silhouettes
    motion.css         durations, easings, keyframes
    components.css     component-scoped rules
  src/components/      reusable, app-agnostic React components
apps/web/
  src/components/      app-specific components ONLY
  src/lib/             pure logic, no JSX
  src/api/             fetching, normalisation, types
  src/app.css          app-local overrides, kept minimal
```

Placement test, applied to every new component: _could another app use this without knowing about relics?_
Yes goes in `packages/ui`. No goes in `apps/web/src/components`.

A file that mixes data fetching, business logic and markup is three files.
Split it: query in `api/`, computation in `lib/`, markup in `components/`.

## 3. Tokens

### 3.1 The mirror must die

`packages/ui/src/styles/tokens.css` currently opens with:

> _Mirror of design-system/tokens.json. Change tokens.json and this file together._

Two files kept in sync by hand always drift.
Replace the mirror with generation.

Add `packages/ui/scripts/build-tokens.mjs`:

```js
/**
 * Generates src/styles/tokens.css from design-system/tokens.json.
 * The JSON is the only place a design value is authored; this file is build output.
 * Run via `npm run build:tokens`, and as the first step of `npm run build`.
 */
import { readFile, writeFile } from "node:fs/promises";

const tokens = JSON.parse(await readFile("../../design-system/tokens.json", "utf8"));

const flatten = (node, path = []) =>
  typeof node === "object" && node !== null && !("value" in node)
    ? Object.entries(node).flatMap(([k, v]) => flatten(v, [...path, k]))
    : [[`--rf-${path.join("-")}`, node.value ?? node]];

const body = flatten(tokens)
  .map(([name, value]) => `  ${name}: ${value};`)
  .join("\n");

await writeFile(
  "src/styles/tokens.css",
  `/* GENERATED by scripts/build-tokens.mjs - do not edit. Edit design-system/tokens.json. */\n:root {\n${body}\n}\n`,
);
```

Adjust `flatten` to the actual shape of `tokens.json`.
Then add to `packages/ui/package.json`:

```json
"build:tokens": "node scripts/build-tokens.mjs",
"build": "npm run build:tokens && node build.mjs && tsc -p tsconfig.build.json"
```

and add `packages/ui/src/styles/tokens.css` to `.gitignore` once generation is proven.

### 3.2 Tokens that are missing and must be added

The current token set covers colour, spacing, notch, motion and z-index well.
It is missing four families that the rules in this document depend on:

```css
/* ---- Typography scale: rem, so browser font-size preference works ---- */
--rf-text-caption: 0.75rem; /* was 12px */
--rf-text-body-sm: 0.8125rem; /* was 13px */
--rf-text-body-md: 0.9375rem; /* was 15px */
--rf-text-body-lg: 1rem; /* was 16px */
--rf-text-heading-sm: 0.875rem;
--rf-text-heading-md: 1rem;
--rf-text-heading-lg: 1.125rem;
--rf-text-display-sm: 1.375rem;
--rf-text-display-md: 1.75rem;
--rf-text-display-lg: 2.25rem;
--rf-text-display-xl: 3rem;

/* ---- Protected geometry: pinned in px ON PURPOSE, never convert ---- */
--rf-touch-target: 44px; /* WCAG 2.5.8 minimum hit area */
--rf-hairline: 1px;

/* ---- Layout width: see rule 4.5. --rf-side DERIVES from --rf-content-max ---- */
--rf-content-max: 1440px; /* widest content; dense tables set this ceiling */
--rf-measure: 68ch; /* reading measure for running prose */
--rf-side: max(var(--rf-space-6), calc((100vw - var(--rf-content-max)) / 2));

/* ---- Breakpoints: named, so a media query never carries a raw number ---- */
--rf-bp-sm: 640px;
--rf-bp-md: 900px;
--rf-bp-lg: 1200px;

/* ---- Reading floor: see rule 4.3 ---- */
--rf-reading-floor: 15px;
```

> **Decided 2026-08-11: this project uses the five breakpoints already in
> `tokens.json`** — `sm 640 / md 768 / lg 1024 / xl 1280 / 2xl 1536` — not the
> three proposed above. Rule 8 makes `tokens.json` the only source of design
> values, `DESIGN_SYSTEM.md` §6.3 already documents what each tier does, and a
> second scale beside the first is exactly the drift this document exists to
> prevent.

Note on breakpoints: CSS custom properties do not work inside `@media` conditions.
Declare the numbers here as documentation and single reference, and either use a
preprocessor/`postcss-custom-media`, or write the literal in the media query with a
comment naming the token. Do not invent a fourth breakpoint without adding it here first.

## 4. The responsive contract

This is the part the project currently does not have at all.
There is exactly one functional media query in the whole frontend.

Three axes, and every value belongs to exactly one of them.

### 4.1 What scales with the WINDOW

Layout, spacing, column counts, panel widths.
These respond to breakpoints and to `clamp()`.
They never respond to the user's font-size preference.

```css
/* Good: the grid reflows, the values come from tokens */
.rf-shell {
  display: grid;
  grid-template-columns: 1fr;
  gap: var(--rf-space-4);
}
@media (min-width: 900px) {
  /* --rf-bp-md */
  .rf-shell {
    grid-template-columns: minmax(0, 1fr) 380px;
  }
}
```

Always use `minmax(0, 1fr)` rather than `1fr` for grid tracks that contain tables or long
unbreakable strings, and set `min-width: 0` on flex children for the same reason.
Without it a wide child forces the whole page to scroll horizontally.

### 4.2 What scales with the USER

Reading text, and only reading text.
Every `font-size` is `rem`.
Never `px`, in CSS or in JSX.

The current codebase has 43 `px` font-size declarations.
All of them must become `rem` at `px / 16`.

### 4.3 What scales with NEITHER

Touch targets, hairline borders, icon boxes, notch depth, blur radii.
These stay pinned in `px` deliberately.
Converting them to `rem` is a bug, not an improvement: a user who enlarges text does not
want a 62px tall button, and a user who shrinks it must not get a 30px tap target.

There is one root rule that makes the whole thing safe:

```css
html {
  /* The browser font-size preference may GROW the text; it may never SHRINK the
     design below the size it was drawn at. On the root element `1rem` resolves to
     the browser's own preference, so max() floors a below-default preference at the
     design baseline while leaving a raised preference completely untouched. */
  font-size: max(1rem, var(--rf-reading-floor));
}
```

This replaces the current `base.css:11` `font-size: 15px`, which hard-overrides the user's
preference in both directions and is a WCAG 1.4.4 failure.

### 4.4 The reference canvases

Every visual change is judged on both of these, never only the large one:

| Canvas    | Size     | Role                                                |
| --------- | -------- | --------------------------------------------------- |
| Reference | 1920x950 | zero-diff canvas; a visual regression here is a bug |
| Small     | 1280x630 | stress canvas; a 1080p panel at 150% OS scaling     |
| Mobile    | 390x844  | the layout must be usable, not merely non-broken    |

A design approved only on the large canvas is not approved.

### 4.5 Maximum content width - the app is currently full-bleed

`App.tsx` gives both the `header` and the `main` an inline `padding: "0 18px"` and nothing else.
There is no page-level `max-width` anywhere in the codebase: the only `max-width` declarations
are local (a 280px tooltip, a 560px dialog, two paragraphs at `68ch`, one 720px column).

The result is that content spans the entire viewport with an 18px gutter, at any width.
On a 1920 monitor that is a 1884px line length; on a 3440 ultrawide it is 3404px.

This is a defect at both ends of the scale:

- **Reading**: a line of prose is comfortable at roughly 45 to 75 characters. Past that the eye
  loses the return sweep and has to hunt for the start of the next line.
- **Scanning a table**: with a wide table the eye has to travel from the item name on the far
  left to its price on the far right, with nothing to anchor it. Widening the table does not add
  information, it adds distance.
- **18px is not a margin, it is an accident.** Content touching the edge of the screen reads as
  unfinished. The gutter must be a deliberate value that grows with the viewport.

#### The rule: outer full-width, inner constrained

Never put `max-width` on the element that carries the background.
Backgrounds, borders and sticky bars stay full-bleed; the content inside them is centred.
Two levels, always:

```html
<!-- outer: full width, owns the background and the border -->
<header class="rf-band">
  <!-- inner: constrained and centred, owns the content -->
  <div class="rf-shell">...</div>
</header>
```

```css
/* Tokens - add to tokens.json */
--rf-content-max: 1440px; /* dense data tables: the app's widest content */
--rf-measure: 68ch; /* prose: comfortable reading measure */
--rf-side: max(var(--rf-space-6), calc((100vw - var(--rf-content-max)) / 2));

.rf-shell {
  max-width: var(--rf-content-max);
  margin-inline: auto;
  padding-inline: var(--rf-space-6);
}

/* Any block of running prose is narrower than the shell, independently. */
.rf-prose {
  max-width: var(--rf-measure);
}
```

`--rf-side` derives from `--rf-content-max`, it is not a second independent number.
Below 1488px it resolves to the 24px minimum gutter; above it, it grows so the content stays
centred at exactly `--rf-content-max`. One token to change, both behaviours follow.

Why `1440px` and not the `1280px` typical of content sites: six of this app's views are dense
tables with eight or more columns. Squeezing those into 1280 forces truncation that costs more
than the extra line length. Do not read this number as universal - it is chosen for this app's
content, and it is the ceiling, not a target.

Two things this rule does NOT ask for:

- The gutter is not fixed. `--rf-side` grows on wide screens by construction; do not hardcode
  a padding next to it.
- Full-bleed is still correct for the things that should touch the edge: the sticky header's
  background and bottom border, page-level scrims, the dialog backdrop. Only their _content_
  gets the shell.

Apply it in this order: `App.tsx`'s header and main first (that alone fixes every view at once),
then remove the now-redundant inline `padding: "0 18px"` from both.

### 4.6 Tables are the hard case here

Six of this app's views are dense data tables with percentage-width columns
(`style={{ width: "26%" }}` and friends).
Percentages do not make a table responsive: they make it shrink until it is unreadable.

Pick one strategy per table and write it down:

- **Horizontal scroll with a sticky first column.** Simplest, honest, works down to 320px.
  Wrap in a container with `overflow-x: auto` and give the wrapper an accessible name plus
  `tabindex="0"` so keyboard users can scroll it.
- **Column priority.** Hide low-priority columns below a breakpoint with a `data-priority`
  attribute and one media query per tier.
- **Card reflow.** Below `--rf-bp-sm`, each row renders as a stacked card.
  Most readable on phones, most work to build.

Do not mix strategies within one table.

## 5. Accessibility

The project already uses `aria-*` in 81 places and has `:focus-visible` styles.
That is a good start and it is currently unverified: nothing in CI checks it.

### 5.1 Hard rules

- Every interactive element is a `<button>`, `<a>`, or a real form control.
  A `<div>` with `onClick` is a defect, regardless of the `role` on it.
- Every focusable element has a visible `:focus-visible` state with at least 3:1 contrast
  against its background. `outline: none` without a replacement is forbidden.
- Every icon-only control has an accessible name (`aria-label`) and a tooltip is not a name.
- Every image has `alt`. Decorative images get `alt=""`, never a missing attribute.
  There is currently exactly one `alt=` in the codebase; audit every `<img>` and every
  inline `<svg>` (decorative SVG gets `aria-hidden="true"` plus `focusable="false"`).
- Data tables use `<th scope="col">` / `<th scope="row">`, and a `<caption>` or
  `aria-labelledby` naming the table.
- Sortable headers expose `aria-sort` and are `<button>` elements inside the `<th>`.
- Dialogs trap focus, restore it on close, close on `Escape`, and use `aria-modal="true"`
  with a labelled title.
- Colour is never the only carrier of meaning. Rarity, tier and vault state must also be
  distinguishable by text or shape, not only by `--rf-rarity-*` hue.
- Live regions: async price updates and toast messages need `aria-live="polite"`.

### 5.2 Contrast

The Orokin theme is dark and warm, which is where contrast quietly fails.
Check every foreground/background pair that ships, in particular:

- `--rf-fg-muted` (`#9a9280`) on `--rf-surface-1` (`#131210`) - verify it clears 4.5:1.
- `--rf-fg-disabled` (`#5c5648`) on any surface - disabled text is exempt from WCAG,
  but if it carries information it is not really disabled.
- `--rf-rarity-uncommon` (`#b8bfc7`) and `--rf-tier-*` chips - these are stated in the
  token file as "chip fills only, never text on dark". Enforce that comment: grep for any
  `color: var(--rf-tier-*)` and remove it.

### 5.3 Motion

`prefers-reduced-motion` is already respected in `motion.css`.
Keep it that way: every new animation, transition over 200ms, and auto-playing effect must
be disabled or reduced under that query.

## 6. Performance

- Fonts are self-hosted already (good). Ensure every `@font-face` carries `font-display: swap`
  and that both woff2 files are `<link rel="preload">`ed from `index.html` if they render
  above the fold.
- The tables use `@tanstack/react-virtual` (good). Verify the virtualiser is actually engaged
  on every list over ~100 rows, not just on the two it was built for.
- `react-query` is present. Give every query an explicit `staleTime`; the market price data
  is refreshed daily server-side, so a `staleTime` of minutes is correct and cuts refetching.
- Never ship a layout that shifts after data loads. Reserve space with a `Skeleton` of the
  same dimensions as the loaded content.
- Measure, do not guess. `npx unlighthouse --site http://localhost:5173` gives per-route
  Core Web Vitals for the whole app in one run.

## 7. Tooling that must exist

The repo currently has no linter, no formatter, no test runner and no accessibility check.
`tsc --noEmit` and a bespoke render check are the only gates.
Add these; they are the cheapest quality you will ever buy.

### 7.1 ESLint with accessibility as an error

```bash
npm i -D eslint @eslint/js typescript-eslint eslint-plugin-react-hooks \
        eslint-plugin-jsx-a11y eslint-config-prettier prettier
```

`eslint.config.mjs` at the repo root:

```js
import js from "@eslint/js";
import ts from "typescript-eslint";
import reactHooks from "eslint-plugin-react-hooks";
import jsxA11y from "eslint-plugin-jsx-a11y";
import prettier from "eslint-config-prettier";

export default ts.config(
  { ignores: ["**/dist/**", "**/target/**", "**/.ds-verify/**"] },
  js.configs.recommended,
  ...ts.configs.recommended,
  {
    files: ["**/*.{ts,tsx}"],
    plugins: { "react-hooks": reactHooks, "jsx-a11y": jsxA11y },
    rules: {
      ...reactHooks.configs.recommended.rules,
      // Accessibility violations BLOCK the build. This is the whole point:
      // a warning nobody reads is not a gate.
      ...Object.fromEntries(
        Object.keys(jsxA11y.configs.recommended.rules).map((r) => [r, "error"]),
      ),
    },
  },
  prettier,
);
```

### 7.2 A no-inline-style gate

Rule 1 is only real if something enforces it.
Add `scripts/lint-inline-style.mjs`:

```js
/**
 * Fails on NEW inline style={{}} occurrences in apps/web and packages/ui.
 * The known count is frozen as a baseline: the gate never fails on existing debt,
 * only on growth. Lower BASELINE as files are cleaned; never raise it.
 */
import { readFileSync, readdirSync, statSync } from "node:fs";
import { join } from "node:path";

const BASELINE = 253; // measured 2026-08-10; see section 9
const roots = ["apps/web/src", "packages/ui/src"];

const walk = (dir) =>
  readdirSync(dir).flatMap((entry) => {
    const p = join(dir, entry);
    return statSync(p).isDirectory() ? walk(p) : p.endsWith(".tsx") ? [p] : [];
  });

const count = roots
  .flatMap(walk)
  .reduce((n, f) => n + (readFileSync(f, "utf8").match(/style=\{\{/g)?.length ?? 0), 0);

if (count > BASELINE) {
  console.error(`inline styles: ${count} (baseline ${BASELINE}) - new inline styles added`);
  process.exit(1);
}
console.log(
  `inline styles: ${count} / ${BASELINE}${count < BASELINE ? " - lower the baseline" : ""}`,
);
```

The same pattern works for a `px`-font-size gate and a raw-hex gate.
A frozen baseline is what makes a rule adoptable on an existing codebase: it stops the
bleeding today and lets the cleanup happen at its own pace.

## 8. Definition of done

Before reporting a frontend task complete, run and paste the real output of:

```bash
npm run typecheck
npm run lint
npm run lint:inline-style
npm run build
```

And confirm by hand, in a browser:

1. The changed view at 1920 wide, 1280 wide, and 390 wide. No horizontal document scroll at any of them.
2. The changed view at 200% browser text zoom. Nothing clipped, nothing overlapping.
3. Tab through the changed view start to finish. Every interactive element receives a visible focus ring, in a sensible order, and `Escape` closes anything that opened.
4. The changed view with `prefers-reduced-motion: reduce` set in devtools rendering settings.

If a step was skipped, say which one and why.
Do not report "verified" for a check that was not run.

## 10. Repair order

Do not attempt all of this at once. In this order, each step is independently shippable:

1. **Root font-size floor** (section 4.3). One line, removes a WCAG failure.
2. **Font-sizes to `rem`** (section 4.2). Mechanical, 43 sites, no visual change at default preference.
3. **The content shell** (section 4.5). Two CSS rules plus three tokens, applied to `App.tsx`'s
   header and main. It fixes every view at once and is the single most visible improvement here.
4. **Tooling** (section 7). ESLint with a11y as error, prettier, the inline-style baseline gate.
5. **Responsive pass, one view at a time** (section 4). Start with the view you use most.
   Tables need the strategy decision in 4.6 before any code is written.
6. **Split the four largest components** (section 9). Extract logic to `lib/`, sub-views to
   sibling components. `WishlistTable.tsx` at 517 lines with 48 inline styles is the best
   first target: splitting it removes debt from two categories at once.
7. **Token generation** (section 3.1). Kills the mirror drift permanently.
8. **Inline-style cleanup**, file by file, lowering the baseline each time.

Steps 1 to 4 are a single afternoon and buy most of the value.
